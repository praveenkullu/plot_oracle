# Plot Protocol: A Decentralized Truth Verification System on Base L2

**Praveen Kullu** · MCS5993 · LTU · 2026

---

## Abstract

The proliferation of AI-generated content and viral misinformation has outpaced manual fact-checking at scale. Plot Protocol addresses this with a blockchain-native truth verification system deployed on Base L2 in which economic incentives — rather than trusted intermediaries — enforce claim quality. Submitters stake USDC bonds that are slashed if their claims are challenged and found false; challengers earn from correctly identified false claims; voters earn fees for correct dispute adjudication. Paraphrase duplicates are surfaced by the same challenger market that polices factual error: a challenger citing an existing verified claim wins the duplicate's slashed bond, eliminating a dedicated novelty oracle. This paper describes the protocol design, its six core modules, a live testnet deployment of 13 smart contracts on Base Sepolia, and end-to-end validation of both the unchallenged and adversarial claim paths.

---

## 1. Introduction

Fact-checking organisations are bottlenecked by human reviewers who cannot match the volume of claims generated by modern media pipelines. Centralised AI-based detection systems introduce trust assumptions that make them unsuitable for adversarial environments. Existing blockchain oracle designs (e.g., UMA, Augur) are optimised for binary financial outcomes, not for the nuanced provenance tracking needed for general factual claims.

Plot Protocol contributes three things:

1. **An optimistic challenge mechanism** that accepts claims by default while allowing any participant to dispute them under economic penalty, producing Verified or Rejected outcomes without a standing reviewer workforce.
2. **A unified challenger market** that handles both factual disputes and paraphrase duplicates under a single bond-and-slash mechanism, eliminating the need for a centralised semantic-similarity oracle.
3. **A permanently archived, confidence-scored record** of every claim outcome, written immutably to Arweave with a verifiable on-chain pointer.

The protocol is deployed on Base L2 for native Circle-minted USDC (no bridge risk), low transaction costs ($0.001–$0.01), and compatibility with EAS, Chainlink, and UMA.

## 2. System Architecture

Plot Protocol uses a two-layer architecture:

```
Layer 1 — On-Chain (Base L2)
  Claim IDs, content hashes, bond escrow, status state machine,
  vote tallies, confidence scores, role-based access control.
  Enforced by 13 smart contracts; immutable and auditable.

Layer 2 — Off-Chain
  Full claim text and evidence on Arweave (permanent, content-addressed).
  Event indexing (Ponder) and REST API (Node.js/Express).
```

### Claim Lifecycle

```
submitClaim()
     │  Bond locked (USDC), status = Submitted
     │  Layer 1: contentHash exact-duplicate check (reverts if seen)
     ▼
NoveltyGate.submitNoveltyResult()  [passthrough — always novel]
     │  status = Pending
     ▼
ChallengeWindow.openWindow()  [2-hour window]
     ├── No challenger ──▶ finalizeUnchallenged() ──▶ Verified  (score = 100)
     └── challenger posts counter-bond ──▶ status = Disputed
                │
                ▼
         InternalVote.openVote() → castVote() → finalizeVote()
                │
                ▼
         OracleRouter.executeResolution()
                ├── submitter wins ──▶ Verified (bond + reward)
                └── submitter loses ──▶ Rejected (bond slashed:
                                         60% challenger, 20% voters, 20% treasury)
```

## 3. Core Modules

### 3.1 Core Data Model (`ClaimRegistry`, `BondEscrow`, `BondCalculator`)

`ClaimRegistry` is the central state machine. Each claim stores:

| Field | Type | Description |
|-------|------|-------------|
| `claimId` | `bytes32` | keccak256 of content hash + submitter + nonce |
| `contentHash` | `bytes32` | keccak256 of claim text (Layer 1 duplicate guard) |
| `bond` | `uint256` | USDC amount locked in `BondEscrow` |
| `status` | `enum` | Submitted → Pending → Disputed → Verified / Rejected / Superseded |
| `selfDeclaredDomain` | `uint8` | Submitter's domain tag (routed to voter pool) |
| `voterAssignedDomain` | `uint8` | Consensus domain tag set after dispute |
| `confidenceScore` | `uint16` | 0–100, set by `ConfidenceScorer` on resolution |

`BondCalculator` maps domain IDs to USDC base bond amounts (governance-adjustable). `BondEscrow` holds and releases USDC via `IERC20.transferFrom` with per-claim accounting.

**Versioning:** A superseded claim stores `nextVersion` and `previousVersion` pointers. No record is ever deleted; stale claims are marked `Superseded` and linked to the corrected claim.

### 3.2 Novelty Detection (`NoveltyGate` + challenger market)

Two mechanisms guard against duplicate submissions:

**Layer 1 — On-chain hash deduplication.** `submitClaim()` reverts immediately if `contentHash` has been seen before, at zero bond cost to the protocol.

**Layer 2 — Challenger-based paraphrase detection.** Semantic duplicates (paraphrases) are surfaced economically rather than algorithmically. A participant who recognises that a new `Pending` claim restates an existing verified claim can call `challenge()` and cite the prior claim ID as counter-evidence in the dispute vote. The challenger wins the submitter's slashed bond; the duplicate is `Rejected`. This eliminates the centralised SNS oracle wallet and its associated trust assumption, at the cost of a reactive detection window (up to 2 hours). A watchdog bot that auto-challenges known paraphrases is planned for v2.

`NoveltyGate.submitNoveltyResult()` is retained in the contract ABI for future use; the backend always submits a passthrough verdict (similarity = 0, no nearest claim) to advance the claim to `Pending`.

### 3.3 Challenge Window (`ChallengeWindow`)

The challenge window implements an optimistic model: the protocol assumes claims are true unless a challenger proves otherwise. Any participant can dispute a `Pending` claim by calling `challenge(claimId, bond)` with a USDC counter-bond equal to the submitter's bond. If no challenger appears within the window (2 hours in v1), a keeper calls `finalizeUnchallenged()` and the claim is `Verified` with a confidence score of 100.

If challenged, the claim transitions to `Disputed` and escalates to the Oracle Router. The challenge window is intentionally short for v1 (Standard tier). Flash (15 min) and Deep (24 hr) tiers are planned via governance.

### 3.4 Oracle Router & Internal Vote (`OracleRouter`, `InternalVote`)

`OracleRouter` is the dispute resolution hub. In v1, all disputes route to `InternalVote`. UMA OOv3 integration is architecturally stubbed for Phase 5.

`InternalVote` implements a simplified three-call vote lifecycle for testnet:

```
openVote(claimId)     — initialises vote record
castVote(claimId, support, weight)  — VOTER_ROLE holders submit
finalizeVote(claimId) — tallies when weightFor or weightAgainst ≥ quorumWeight
```

On finalisation, `InternalVote` calls `OracleRouter.executeResolution()` which:
- Sets claim status (`Verified` or `Rejected`) on `ClaimRegistry`
- Releases or slashes bonds via `BondEscrow`
- Records the final confidence score via `ConfidenceScorer`

In production, commit-reveal voting and Chainlink VRF jury selection are planned; testnet uses a single-voter quorum (quorumWeight = 1) with the operator wallet holding `VOTER_ROLE`.

### 3.5 Confidence Scoring (`ConfidenceScorer`)

The confidence score (0–100) is a weighted sum of observable on-chain signals:

```
Score = w1·ChallengerExposure + w2·DomainPoolDepth
      + w3·CitationDiversity  + w4·StakeRatio
      + w5·TimeInWindow
```

Weights are governance-adjustable per domain. Unchallenged claims receive score = 100. Disputed claims receive a score computed from vote margins and exposure metrics.

Three display labels map to score ranges:

| Score | Label | Meaning |
|-------|-------|---------|
| 70–100 | Verified | Survived active adversarial scrutiny |
| 30–69 | Unchallenged | Passed window with limited scrutiny |
| 0–29 | Unchecked | Minimal challenger coverage |

### 3.6 Token Economics (`PLOTToken`, `EmissionController`, `GovernorPlot`, `Treasury`)

Plot Protocol uses a dual-asset model:

- **USDC** — bonds, challenger counter-bonds, voter fees, bounties. Native Circle-minted on Base (no bridge risk).
- **PLOT** — governance voting, staker revenue share, protocol access licence.

**Bond flow:**

| Outcome | Submitter Bond | Challenger Bond |
|---------|---------------|-----------------|
| Unchallenged (Verified) | Returned + reward | — |
| Challenged, submitter wins | Returned + challenger's bond | Slashed |
| Challenged, submitter loses | Slashed (60% → challenger, 20% → voters, 20% → treasury) | Returned + reward |

**Governance:** `GovernorPlot` (OpenZeppelin Governor + `TimelockController`) enforces a 14-day delay on parameter changes. Bond amounts cannot change by more than 25% per vote. A Foundation multisig retains veto rights for the first two years.

**Emissions:** `EmissionController` implements a decreasing-rate emission schedule with a hard floor at 20% of Year-1 output. Chainlink Price Feed circuit breakers pause emissions and trigger buybacks if PLOT/USD drops >30% in 24 hours.

### 4.2 Off-Chain Services

Three services run under PM2:

| Port | Service | Stack |
|------|---------|-------|
| 3000 | REST API | Node.js / Express (TypeScript) |
| 42069 | Event Indexer | Ponder 0.7 (TypeScript) |

The REST API (`backend/`) exposes `POST /claims` (submit a claim end-to-end: escrow → NoveltyGate passthrough → `openWindow()`) and `GET /claims/:id` (fetch current state). The Ponder indexer listens for on-chain events and writes indexed state (claims, challenge windows, vote records, emissions) to a local PGlite database, serving GraphQL queries on port 42069.

### 4.3 Role Access Control

All privileged functions are gated by OpenZeppelin `AccessControl`. Critical roles:

| Role | Holder | Controls |
|------|--------|---------|
| `ORACLE_ROUTER_ROLE` | OracleRouter, ChallengeWindow | ClaimRegistry state transitions, BondEscrow release/slash |
| `NOVELTY_GATE_ROLE` | NoveltyGate | `recordNoveltyResult()` on ClaimRegistry |
| `INTERNAL_VOTE_ROLE` | InternalVote | `executeResolution()` on OracleRouter |
| `VOTER_ROLE` | Registered voters | `castVote()` on InternalVote |
| `SNS_ORACLE_ROLE` | Relay wallet | `submitNoveltyResult()` on NoveltyGate (passthrough; SNS oracle removed) |

## 5. Evaluation

Two end-to-end test scripts validate both lifecycle paths on live Base Sepolia:

### 5.1 Unchallenged Path (`scripts/test/e2e-claim.sh`)

Tests the happy path: submit → NoveltyGate passthrough → Pending → keeper finalises window → Verified.

**Result: 7/7 PASS** (commit `8b644d9`)

| Step | Check |
|------|-------|
| 1 | Services healthy (backend, Ponder) |
| 2 | Claim submitted, `ClaimSubmitted` event emitted, bond locked |
| 3 | Backend pushes claim to `Pending` via `NoveltyGate` passthrough; `NoveltyResult` indexed |
| 4 | `WindowOpened` event emitted, challenge window active |
| 5 | Keeper calls `finalizeUnchallenged()` after window expires |
| 6 | Backend API returns status = `Verified` |
| 7 | Ponder GraphQL returns claim record with correct final state |

### 5.2 Adversarial Dispute Path (`scripts/test/e2e-dispute.sh`)

Tests the full dispute branch: submit → Pending → `challenge()` → Disputed → `openVote()` → `castVote()` → `finalizeVote()` → `executeResolution()` → Verified/Rejected.

**Result: 17/17 PASS** (commit `3a2c019`)

| Step | Checks |
|------|--------|
| 0 — Pre-flight | Services healthy, VOTER_ROLE granted, quorumWeight = 1 |
| 1 — USDC balance | Challenger wallet holds ≥ 1 USDC |
| 2 — Submit claim | Claim submitted; NoveltyGate passthrough; window opened |
| 3 — Challenge | USDC approved; `challenge()` called; status = `Disputed` |
| 4 — Vote | `openVote()` → `castVote()` → `finalizeVote()` all succeed |
| 5 — Resolution | `executeResolution()` sets final status; bond settled |
| 6 — Ponder index | GraphQL confirms `voteRecord` and final claim state indexed |

Notable issues resolved during testing:
- `ChallengeWindow` requires `ORACLE_ROUTER_ROLE` on `ClaimRegistry` to call `markDisputed()` — granted post-deployment.
- Ponder 0.7 historical store does not expose Drizzle `select()`; `VoteCast` handler migrated to `context.db.find()`.
- `cast send --json` receipts omit `transactionHash`; all scripts switched to plain-output `awk` parsing.

## 6. Security Considerations

**Bond as spam filter.** Every submission puts ≥ $1 USDC at risk (testnet; production bonds $100–$2,500). This eliminates low-cost spam without a reputation system or identity gate.

**Role minimisation.** No contract holds a role it does not need. `ChallengeWindow` was audited to require `ORACLE_ROUTER_ROLE` only because it calls `markDisputed()` on `ClaimRegistry`; this was a post-deployment discovery, now documented.

**Reentrancy.** `BondEscrow` uses OpenZeppelin `ReentrancyGuard` on all fund movement functions. `ClaimRegistry` emits events before any external call.

**Sequencer risk.** Base uses a centralised sequencer (standard for OP Stack L2s). A sequencer outage affects liveness but not safety — state is committed to L1, and the challenge window timer is based on `block.timestamp`, which pauses with the chain. L1 force-inclusion is available as a fallback.

**Oracle trust.** VOTER_ROLE holders are trusted in v1. Production deployment moves to commit-reveal + VRF jury selection for voters, eliminating single-wallet trust. The SNS oracle wallet is no longer a trust assumption; duplicate detection is fully decentralised via the challenger market.

## 7. Limitations and Future Work

| Item | Status | Notes |
|------|--------|-------|
| Commit-reveal voting | Planned | v1 uses plain `castVote`; no front-running protection |
| Chainlink VRF jury selection | Planned | v1 uses static VOTER_ROLE grant |
| UMA OOv3 escalation | Stubbed | Interface present; integration deferred to Phase 5 |
| Chainlink Automation keepers | Planned | v1 uses manual keeper scripts |
| Arweave permanent storage | Stubbed | Content stored off-chain; Irys upload not wired in v1 |
| Flash / Deep verification tiers | Deferred | Governance-activatable |
| Gnosis Safe multisig | Mainnet only | Treasury uses EOA on testnet |
| Anti-Sybil voter credentials | Deferred | EAS attestations planned for domain expertise proofs |
| Paraphrase detection latency | By design | Challenger-based detection is reactive; a duplicate may sit `Pending` for up to 2 hours before being challenged. A watchdog bot that auto-challenges known paraphrases is planned for v2. |

The most significant limitation is the single-voter quorum used on testnet. Production will require ≥ 15 randomly-selected voters from a PLOT-staked domain pool before a vote can finalise.

---

## 8. Conclusion

Plot Protocol demonstrates that economic incentives alone — without a standing reviewer workforce or trusted AI system — can enforce factual claim quality at scale. The optimistic challenge model keeps costs near-zero for true claims while making false claims expensive to publish. The same challenger market that polices factual error also surfaces paraphrase duplicates, eliminating a dedicated novelty oracle and the trust assumptions it carried. All 13 contracts are live on Base Sepolia; both claim paths (unchallenged and adversarial dispute) pass end-to-end validation on a live testnet.

The next production milestones are commit-reveal voting, Chainlink VRF jury selection, and UMA escalation — features that increase the protocol's adversarial robustness without changing the core bond-and-challenge economic model.
